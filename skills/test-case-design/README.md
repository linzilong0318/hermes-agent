# 测试用例设计技能 — 设计思路文档

> 本文档从**业务设计**与**多 Agent 编排**两个核心视角，阐述 `test-case-design` 技能的整体设计思路，不展开功能细节。

---

## 一、定位与边界

### 1.1 技能定位

本技能是一个**功能测试用例全流程生成器**，覆盖从"需求文档"到"可评审用例 + 可上传结构化数据"的完整链路：

```
需求文档(PDF/DOCX) → 需求分析 → 测试点提取 → 用例编写 → 用例评审 → 上传后端 + 生成文档
```

它**只做"写用例"这一件事**，明确不做：测试计划、测试策略、自动化脚本、接口测试、性能测试。这种"窄而深"的定位是整个设计的前提——只有边界清晰，Agent 才不会在执行中漂移。

### 1.2 运行环境

本技能部署在 **Hermes Agent 实例**中，通过 **Hermes API Gateway** 对前端提供对话式接口：

- 前端通过 Hermes API Gateway 发起会话，每个会话有一个 `sessionId`
- 技能通过环境变量 `HERMES_SESSION_ID` 获取会话标识，串联多轮对话
- 技能内部通过 Nacos 服务发现后端业务服务，完成用例与文档的上传

这意味着技能的输入是"自然语言对话"，输出是"结构化数据 + 可读文档"，而 Hermes 平台负责会话管理与上下文保持。

### 1.3 反向排除（边界守卫）

技能在最入口处设置了**反向排除规则**，优先于阶段识别执行：一旦识别到 UI 测试平台元数据字段（`projectUid`、`folderUid`、`relativePath` 等）或"创建 Web 测试脚本"等句式，立即转交给 `playwright-e2e-workflow` 技能，不进入自身流程。

这是一个关键的架构决策：**用"先排除"代替"后纠偏"**，避免错误进入流程后产生大量无效中间产物。

## 二、整体业务流程设计

### 2.1 五阶段流水线

整个技能按"阶段递进 + 人工确认门"的方式组织，共五个阶段：

| 阶段 | 名称 | 核心产出 | 是否需用户确认 |
|------|------|---------|--------------|
| 一 | 需求分析 | 8 维度评估表 + 待澄清问题 | 有待澄清问题时强制停止 |
| 二 | 测试点提取 | 测试点清单（含优先级/风险/来源） | 是 |
| 三 | 用例编写 | 测试用例 MD（供评审） | 是 |
| 四 | 用例评审与上传 | 评审报告 + 用例 JSON 上传 + PDF 文档 | 评审通过后自动上传 |
| 五 | 清理与总结 | 临时文件清理 + 完成总结 | — |

### 2.2 设计原则：阶段解耦 + 强制确认门

每个阶段之间设有**强制确认门**：

- 阶段一发现待澄清问题时，**禁止自动进入阶段二**，必须等待用户回复
- 阶段二测试点清单需用户确认后才进入阶段三
- 阶段三用例需用户确认后才进入阶段四
- 阶段四评审通过后才触发上传

这种设计的核心目的是**把"AI 的自主性"约束在单阶段内，把"跨阶段的决策权"交给人类**。AI 可以在一个阶段内深度思考、并行加速，但不能擅自推进流程。这避免了"AI 假设答案继续往下走"导致的错误累积。

### 2.3 设计原则：方法论固化

技能将业务方的方法论固化为可执行的检查框架，而非依赖 Agent 的"经验"：

- **需求分析**：8 维度检查框架（功能完整性、逻辑一致性、边界清晰度、可测试性、数据完整性、异常处理、依赖关系、性能要求）
- **测试点提取**：8 维度扫描（功能、数据、场景、非功能、组合、状态转换、并发、依赖）
- **用例编写**：8 种测试设计方法（等价类、边界值、判定表、因果图、状态迁移、场景法、正交试验、错误推测）+ 表单场景规则 + 集成场景规则
- **用例评审**：4 维度评审（完整性、准确性、有效性、可执行性）

这些框架的本质是**把"隐性测试经验"显性化为"显性检查清单"**，让 Agent 每次执行都遵循同一套标准，保证产出质量的稳定性。

## 三、多 Agent 编排设计

这是本技能最核心的架构亮点。技能采用 **"主 Agent 编排 + 子 Agent 执行"** 的模式，在关键环节引入子 Agent 以解决单 Agent 的固有盲区。

### 3.1 编排总览

```
┌─────────────────────────────────────────────────────┐
│                   Main Agent                         │
│   职责：流程编排、阶段切换、参数提取、结果汇总        │
│         用户交互、确认门守卫、最终上传                │
└──────────┬──────────────────────┬───────────────────┘
           │                      │
     ┌─────▼──────┐        ┌──────▼───────┐
     │ 阶段三并行  │        │ 阶段四独立    │
     │ Writer 子  │        │ Reviewer 子   │
     │ Agent (×N) │        │ Agent         │
     └────────────┘        └───────────────┘
```

### 3.2 阶段三：并行 Writer 子 Agent

**问题背景**：当测试点覆盖多个模块、用例总数较多时，单 Agent 串行编写存在两个问题——效率低、上下文过长导致后期用例质量下降。

**编排策略**：

1. **触发条件**：测试点覆盖 ≥ 2 个模块 或 预估用例 ≥ 25 条
2. **拆分维度**：按模块拆分（以测试点清单中的 `## [模块名称]` 为边界）
3. **并行上限**：同时 spawn 的子 Agent 不超过 3 个，超出串行排队
4. **上下文隔离**：每个子 Agent 的 context 只包含该模块的需求片段 + 该模块的测试点 + 通用设计方法，不包含其他模块信息
5. **编号防冲突**：用例编号格式 `TC-[模块]-[序号]`，模块标识天然隔离编号空间
6. **独立持久化**：每个子 Agent 写入独立的 MD 文件，由 Main Agent 统一合并

**合并后校验**（Main Agent 执行）：

| 检查项 | 说明 |
|--------|------|
| 编号唯一 | 无重复编号 |
| 覆盖率 100% | 原测试点清单的每个点都有用例覆盖 |
| 无冗余 | 同一测试点不应被多个用例重复覆盖 |
| 模块完整性 | 所有模块的测试点都已编写 |
| 具体数据 | 抽查各模块用例，步骤使用了具体值 |

**设计要点**：并行不是为了"快"，而是为了**让每个子 Agent 聚焦单一模块，提升深度**。上下文越短，Agent 对该模块的思考越充分。

### 3.3 阶段四：独立 Reviewer 子 Agent

**问题背景**：Main Agent 自己评审自己编写的用例存在固有盲区——编写时的思维惯性会带入评审，"我这么写是因为我当时考虑了 X"，容易忽略步骤模糊、数据缺失等问题。覆盖率的"自己数"容易自我安慰。

**编排策略**：

1. **角色分离**：Reviewer 子 Agent 的角色是"独立测试用例评审专家"，与 Writer 完全分离
2. **上下文裁剪**：Reviewer 的 context **只包含三样东西**——需求原文片段 + 测试点清单 + 待评审用例，**刻意排除 Main Agent 写用例时的推理过程**，保证无偏见
3. **明确职责**：4 维度严格评审（完整性、准确性、有效性、可执行性），给出覆盖率数据和明确"通过/不通过"结论
4. **循环机制**：

   | Reviewer 结论 | Main Agent 动作 |
   |--------------|----------------|
   | ✅ 通过 | 进入上传环节 |
   | ❌ 不通过 + 缺失场景清单 | 补充用例 → 重新 spawn Reviewer 复查 → 循环直到通过 |

**设计要点**：这是"自我审查"向"独立审查"的升级。通过**上下文裁剪**实现"信息隔离"，让 Reviewer 天然从"执行者"角度审视用例，而不是从"作者"角度辩护。

### 3.4 编排的核心思想

整个多 Agent 编排遵循三个核心思想：

1. **职责分离**：Main Agent 负责"流程与决策"，子 Agent 负责"深度执行与独立审查"
2. **上下文隔离**：每个子 Agent 只拿到它需要的最小上下文，避免信息污染
3. **闭环校验**：Writer 产出 → Reviewer 审查 → 不通过则回退补充 → 再审查，形成闭环

这种编排本质上是在用"组织架构"弥补"单 Agent 能力边界"——不是让一个 Agent 做所有事，而是让不同 Agent 在不同环节发挥各自优势。

## 四、数据流与状态管理

### 4.1 会话状态串联

技能通过 `sessionId` 串联多轮对话，所有中间状态都持久化在以 sessionId 隔离的临时目录中：

```
/opt/data/tmp/test-case-design/{sessionId}/
├── requirements.pdf              # 阶段一产出
├── test_points_{batchNo}.md      # 阶段二产出
├── test_cases_{batchNo}.md       # 阶段三产出（供评审）
├── cases_payload.json            # 阶段四产出（供上传）
├── 待澄清需求清单_{batchNo}.md/pdf
├── 测试用例评审报告_{batchNo}.md/pdf
└── scripts/                      # 临时脚本
```

**设计要点**：

- **文件即状态**：不依赖内存状态，所有阶段产出都落盘，使得跨轮次对话可恢复
- **sessionId 隔离**：不同会话的临时文件互不干扰，支持并发会话
- **batchNo 批次**：`yyyyMMddHHmmssSSS`（17 位），同一批次所有用例共享，便于后端追溯
- **统一清理**：阶段五执行 `rm -rf` 统一清理，不残留

### 4.2 双格式产出策略

阶段三同时产出两种格式，服务于不同消费者：

| 格式 | 消费者 | 用途 |
|------|--------|------|
| Markdown | 人类（评审报告） | 可读性强，供 Reviewer 评审和用户确认 |
| JSON | 后端 API | 结构化，供 `/api/v1/testcase/save` 接口上传 |

**设计要点**：不在阶段三生成 JSON，而是**评审通过后才生成 JSON 并上传**。这避免了"评审未通过就上传脏数据"的问题——上传时机被严格约束在评审通过之后。

### 4.3 数据流全景

```
用户请求(docUrl)
    │
    ▼
[阶段一] download_requirements.py → requirements.pdf
    │   解析 → 8维度分析 → 待澄清问题(强制停止)
    ▼
[阶段二] test_points_{batchNo}.md (持久化)
    │   8维度提取 → 优先级/风险评估 → 用户确认
    ▼
[阶段三] 并行 Writer 子Agent → test_cases_{batchNo}.md (持久化)
    │   8种设计方法 + 表单规则 + 集成规则 → 合并校验
    ▼
[阶段四] Reviewer 子Agent → 评审报告
    │   不通过? → 回阶段三补充 → 循环
    │   通过? → 生成 cases_payload.json
    │            → upload_cases.py → 后端 /api/v1/testcase/save
    │            → md_to_pdf.py → PDF
    │            → upload_file.py → 后端 /api/v1/file/upload
    ▼
[阶段五] rm -rf 清理 → 返回总结(含文档链接)
```

## 五、与后端系统的集成设计

### 5.1 服务发现架构

技能不硬编码后端地址，而是通过 **Nacos 服务发现**动态获取后端实例：

```
环境变量(NACOS_*) → NacosClient → discover_service → (ip, port) → build_url → call_api
```

**设计要点**：

- **环境变量注入**：Nacos 配置通过环境变量传入，技能本身不存储任何连接信息
- **健康实例筛选**：从 Nacos 返回的实例列表中筛选 `healthy=True` 的实例
- **通用模块复用**：`discover_and_call.py` 作为通用模块，被 `upload_cases.py` 和 `upload_file.py` 复用

### 5.2 两个后端接口

| 接口 | 用途 | 调用方式 |
|------|------|---------|
| `/api/v1/testcase/save` | 上传结构化用例 JSON | JSON POST |
| `/api/v1/file/upload` | 上传 PDF 文档（评审报告/澄清清单） | multipart/form-data |

### 5.3 脚本固化策略

技能将所有"与外部系统交互"的逻辑固化成独立 Python 脚本，而非让 Agent 内联执行：

| 脚本 | 职责 |
|------|------|
| `download_requirements.py` | 需求文档下载（重试 + 中文 URL 编码） |
| `discover_and_call.py` | Nacos 服务发现 + REST 调用通用模块 |
| `upload_cases.py` | 用例 JSON 上传 |
| `upload_file.py` | PDF 文件上传 |
| `md_to_pdf.py` | Markdown → PDF 转换 |

**设计要点**：脚本固化的核心目的是**把"易错的 IO 操作"从 Agent 的不确定性中剥离出来**。Agent 调用脚本只需传参数，脚本内部处理重试、编码、异常捕获、服务发现等复杂逻辑，保证 IO 行为的可预期性。

## 六、安全设计

### 6.1 多层脱敏体系

技能在多个层面设置了脱敏规则，形成纵深防御：

| 层面 | 规则 |
|------|------|
| 环境变量 | 禁止输出 `NACOS_*`、含 `TOKEN/PASSWORD/SECRET/KEY/CREDENTIAL` 的变量值 |
| 脚本输出 | 敏感变量值仅保留前 4 字符 + `***` |
| curl 命令 | Token/密码替换为 `{REDACTED}` |
| 日志 | Python 脚本打印环境变量时只打印变量名 |
| API 响应 | 后端返回的敏感字段展示前必须脱敏 |
| 业务 ID | `sessionId`、`project_id`、`user_id` 等禁止展示给用户 |

### 6.2 安全规则的最高优先级

安全规则被标注为"最高优先级，必须遵守"，在整个技能执行过程中任何情况下不得违反。这是一个**约束优先于能力**的设计哲学——宁可功能受限，也不能泄露敏感信息。

## 七、关键设计决策总结

| 决策 | 动机 | 收益 |
|------|------|------|
| 五阶段 + 强制确认门 | 防止 AI 自主推进导致错误累积 | 跨阶段决策权归人类 |
| 方法论固化（8×4 框架） | 把隐性经验显性化 | 产出质量稳定可复现 |
| 并行 Writer 子 Agent | 单 Agent 上下文过长导致质量下降 | 聚焦单模块，提升深度 |
| 独立 Reviewer 子 Agent | 自我审查存在固有盲区 | 上下文裁剪实现无偏见审查 |
| 上下文隔离 | 避免信息污染 | 每个子 Agent 聚焦职责 |
| 文件即状态 | 不依赖内存 | 跨轮次可恢复 |
| 评审通过后才上传 | 避免上传脏数据 | 数据质量保障 |
| 脚本固化 IO 操作 | 剥离 Agent 不确定性 | IO 行为可预期 |
| Nacos 服务发现 | 不硬编码地址 | 环境无关，可移植 |
| 反向排除优先 | 先排除后纠偏 | 避免无效中间产物 |
| 安全规则最高优先级 | 约束优先于能力 | 防止敏感信息泄露 |

## 结语

本技能的核心设计思想可以概括为一句话：**用流程约束 Agent 的自主性，用多 Agent 编排突破单 Agent 的能力边界，用方法论固化保证产出质量，用脚本固化保证 IO 可靠性**。

它不是一个"让 AI 自由发挥"的技能，而是一个"把 AI 嵌入工程化流水线"的技能——每个环节都有明确的输入输出、校验机制和回退路径，AI 的创造力被引导到"深度执行"而非"流程决策"上。这种设计使得技能在商业场景下具备可预期的稳定性，而非依赖单次 Prompt 的运气。
