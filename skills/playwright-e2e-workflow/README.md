# Playwright E2E 测试技能 — 业务设计说明

> 本文档侧重**业务设计思路**，不展开功能细节。目标是讲清楚"为什么这样设计"。

---

## 一、业务定位

### 1.1 要解决的问题

Web 项目的端到端（E2E）测试长期存在两个痛点：

1. **编写成本高**：测试脚本需要真实环境、真实登录态、真实页面结构，人工编写耗时且容易因定位器漂移而失效。
2. **维护成本高**：页面迭代后脚本批量失败，修复需要重新理解用例意图、重新探索页面、逐个修定位器，工作量不亚于重写。

本技能把这两件事交给 AI Agent 自动完成：**给定一个 Web 功能描述，Agent 自主探索页面、设计测试计划、编写 Playwright 脚本、自验证到全绿、产出报告并回传后端**；对于已有脚本，Agent 能下载、理解意图、定位失败点、修复后回传。

### 1.2 在系统中的位置

```
前端 ──HTTP──> Hermes API Gateway ──> Hermes Agent 实例
                                          │
                                          ├── 加载本技能（SKILL.md + scripts/ + references/）
                                          │
                                          ▼
                                   会话工作区（/opt/data/e2e/<sessionId>）
                                          │
                                   ┌──────┴──────┐
                                   │             │
                              后端测试平台    被测 Web 应用
                             （配置/产物闭环）  （Playwright 驱动）
```

- **技能宿主**：本技能以 SKILL.md 形式挂载在 Hermes Agent 实例中，由 Agent 按触发条件加载。
- **接口暴露**：前端不直接调用技能，而是通过 Hermes API Gateway 与 Agent 交互；Agent 在会话内编排技能的各阶段脚本。
- **测试框架**：统一使用 Playwright Test，CLI 方式驱动（`npx playwright test`），不依赖 MCP。

### 1.3 两个核心业务场景

| 场景 | 触发语 | 输入 | 产出 |
|------|--------|------|------|
| **场景 A：AI 生成测试脚本** | "请帮我创建 Web 测试脚本" | 项目空间、目录、功能名、页面路径、描述、关联用例、静态资源 | 新脚本 + 测试计划 + 报告，回传后端建库 |
| **场景 B：AI 执行并修复已有脚本** | "请帮我执行并修改 Web 测试脚本" | 功能 UID（functionUid） | 修复后的脚本 + 新报告，回传后端覆盖 |

两个场景共享同一套工作区、同一套环境就绪流程、同一套探索与自验证机制，只在**输入解析**和**收尾上传**两个环节分叉。

## 二、整体设计思路

### 2.1 设计原则

1. **后端是唯一事实来源**：基准配置（Playwright config、global-setup）、资源清单、已有脚本，全部从后端接口拉取，不在本地伪造。接口不可达即阻塞上报，绝不猜配置。
2. **会话隔离**：每个会话一个独立工作区目录，多用户/多会话并发互不干扰。隔离边界是 Hermes 注入的 `HERMES_SESSION_ID`。
3. **Agent 编排，脚本固化**：流程的"决策"交给 Agent（理解需求、设计用例、修定位器），"机械操作"固化成 Python/Node 脚本（拉配置、上传、清理）。Agent 不手写 curl、不拼 heredoc。
4. **自验证闭环**：任何脚本在回传前必须本地跑通（`npx playwright test` 全绿），失败即修，修不好如实标记 `fixme`。不把"没跑过的脚本"交给后端。
5. **失败安全**：后端建库是"只有成功才落库"的语义，失败可安全重试；上传支持续传（已上传的产物 URL 传回，只重跑建库步骤）。

### 2.2 为什么是"会话工作区 = 真实目录"而非临时目录

早期版本（4.x）曾用 `.mcp/<pid>` 目录 + ppid 链自发现 + 指针文件来对齐 MCP server 的工作区。5.0 起移除全部 MCP，改为：

```
/opt/data/e2e/<HERMES_SESSION_ID>/
```

- **sid 由 Hermes 显式注入**子进程环境，是契约行为，不依赖进程模型探测（避免模型漂移）。
- **Agent 与 CLI 读写同一目录**：Agent 用 `write_file` 写脚本，CLI 用 `npx playwright test` 跑脚本，两者看到的是同一份文件，无需同步。
- **场景 B 天然无覆盖问题**：前端触发修复时开新会话 → 新 sid → 新目录，不会覆盖别的会话的产物。

### 2.3 为什么用 Python 脚本封装后端交互

后端交互涉及：Nacos 动态服务发现、双 envelope 格式兼容、multipart 上传、退出码语义、续传重试。这些逻辑如果让 Agent 每次手写 curl，既容易出错也难以审计。固化成四个脚本后：

- **Agent 只需传参数**，不关心前缀解析、envelope 判定。
- **退出码即语义**：0 成功、2 业务错误（停下询问用户）、1 系统错误。
- **踩坑经验沉淀在脚本里**，而非散落在 Agent 的每次推理中。

## 三、流程编排设计

整个流程分为 7 个阶段（0–6），两个场景在阶段 0–2 共用，阶段 1.5 和阶段 6 分叉。

```
阶段 0  环境就绪 + 工作区体检        ◄── 两场景共用
  │
阶段 1  拉基准配置 + 物化 + 登录      ◄── 两场景共用（参数不同）
  │
阶段 1.5 下载待修复产物              ◄── 仅场景 B
  │
阶段 2  探索页面 + 编写测试计划       ◄── 两场景共用
  │
阶段 3  编写/修改测试脚本            ◄── A: 新写 / B: 在旧脚本上修
  │
阶段 4  自验证 + 修复（跑到全绿）     ◄── 两场景共用
  │
阶段 5  生成 JSON 报告              ◄── 两场景共用
  │
阶段 6  上传产物 + 清理              ◄── A: 裸传+建库 / B: 业务端点整表替换
```

### 3.1 阶段 0：环境就绪（每轮必跑）

**设计意图**：容器环境是共享的、有状态的（Xvfb 进程、node_modules、上次会话的残留），每轮开头必须体检并自愈。

- 同步技能脚本到工作区（权威副本在技能目录，运行副本每次覆盖，防止被改脏）。
- 按 sid 确定性分配 Xvfb display 号（`99 + sha1(sid) % 16`），多会话并发各用各的 display。
- 初始化共享 `node_modules`（软链全局 playwright 包，各会话配置加载器向上解析自动命中）。

**关键决策**：display 号用 sid 哈希确定性分配，而非随机或递增。这样同一会话重启能复用同一 display，避免泄漏。

### 3.2 阶段 1：拉基准配置 + 物化

**设计意图**：测试配置不能本地硬编码，必须来自后端——因为不同项目可能有不同的 baseURL、global-setup（含登录账号与目标空间）。

- `fetch_config.py` 调 `config/detail` 接口，把后端下发的 `playwrightConfig` 和 `globalSetup` 写入 `template/`（只读，永不手工改）。
- `prepare.mjs` 把 `template/` 物化成可运行的 `playwright.config.ts` + `global-setup.ts`，并打补丁：storageState 绝对路径、headless、`--no-sandbox`、浏览器归一化（强制 chromium）、CR-only 行尾归一化。
- 登录态独立：每会话 `auth.json`，与 Hermes 凭据库 `/opt/data/auth.json` 物理隔离，互不污染。

**关键决策**：浏览器字段归一化。后端可能下发 `msedge`/`firefox`，但容器只装了 chromium。与其尝试安装缺失浏览器，不如统一归一化到 chromium——E2E 测试关心的是业务逻辑，不是浏览器差异。

### 3.3 阶段 1.5：下载待修复产物（仅场景 B）

**设计意图**：修复不是从零重写，必须基于原脚本的用例意图。下载三样东西：

- **旧脚本** → `tests/`（修复对象）
- **旧计划** → `specs/`（对齐用例意图，不上传不保留）
- **旧报告** → `report/prev-test-results.json`（找上次失败点，直接丢弃）

旧计划只用来"理解原来想测什么"，不参与回传——因为修复后用例意图不变，没必要重传计划。

### 3.4 阶段 2：探索 + 测试计划

**设计意图**：AI 写测试脚本最大的坑是"凭空想象页面结构"。本阶段强制 Agent **先看真实页面再写**。

- `probe-*.mjs` 模板带登录态真实访问页面，dump 出 DOM 结构、可交互元素、中文文案。
- 探索结果沉淀到 `references/` 目录（如设备类型页、设备管理页的定位器手册），下次同页面测试可直接复用，省大量 probe 往返。
- 测试计划（`*.plan.md`）是"设计"产物：正常路径 + 边界 + 校验失败各成场景，步骤注释对应 plan 步骤。

**关键决策**：中文界面不翻译。login.mjs 强制切简体中文，probe 看到的就是中文 UI，定位器直接用中文文案（如 `button:has-text("新增")`），不做中英文转换——因为被测系统就是中文界面，测试就该贴合真实。

### 3.5 阶段 3–4：编写 + 自验证闭环

**设计意图**：这是"AI 写代码"的核心环节，设计上强调**闭环**和**归因**。

- 场景 A 按计划手写脚本；场景 B 在旧脚本上修 bug（不重写）。
- 跑 `npx playwright test`，失败看终端报错 + `test-results/`（错误快照/trace）。
- 修选择器/时序/断言后重跑，直到全绿。
- 顽固问题允许 `test.fixme()` + 注释原因，不硬造假通过。

**关键决策**：禁止给关键断言套 `.catch(() => {})`。吞断言会让失败被隐藏，后续报错无法精确归因。判据顺序必须是"先等成功态真的出现，再断言后续 DOM"。

### 3.6 阶段 5–6：报告 + 上传 + 清理

**设计意图**：产物必须回传后端形成闭环，且上传后清理工作区，避免残留干扰下一轮。

**场景 A 的上传设计**（三步走）：
1. 三个产物（脚本/计划/报告）各自裸传 MinIO，拿到 `previewUrl`。
2. 调 `function/save` 建库，body 带元数据 + `resourceList`（三个 previewUrl）。
3. `functionUid` 可选：空 = 新建记录；传真实值 = 覆盖更新历史记录。

**场景 B 的上传设计**（业务端点整表替换）：
- 调 `biz` 端点 `/api/v1/file/upload`，按 `type`（TEST_SCRIPT/TEST_REPORT）上传。
- 后端按类型整表替换：上传 TEST_SCRIPT 即清空旧 scriptList 换成新的，不会出现新旧两条。
- 自动绑定 functionUid，无需 `function/save`。

**为什么两个场景用不同上传端点**：
- 场景 A 是"新建"，需要先有文件再有库记录，所以走"裸传 → 建库"两步。
- 场景 B 是"更新"，functionUid 已存在，业务端点能自动绑定并整表替换，一步到位。

**清理设计**：`cleanup.mjs` 清空 session 目录全部文件（仅留空目录），带路径守卫（只允许 `/e2e/<会话id>` 形态，误跑直接拒绝）。上传失败时不清理，保留产物待后端恢复后重传。

## 四、关键设计决策汇总

### 4.1 functionUid 的双语义（场景 A）

| 传参 | 语义 | 收尾行为 |
|------|------|----------|
| 空/缺失 | 新建记录 | `function/save` 返回新 functionUid |
| 传真实值 | 覆盖更新 | `function/save` body 透传，删除历史记录并新建 |

这个设计让"重写某个功能的测试"也能走场景 A 全流程（探索/计划/编写/自验证不变），只是收尾时告诉后端"这是对历史记录的覆盖"。

### 4.2 静态资源的两层失效处理

- **第一层（写脚本前）**：用户给的资源 UID 可能抄错。`fetch_config` 过滤后若全部未命中，先跑 `--list-resources` 核对近失（文件名与功能描述吻合度），有近匹配则确认后继续，无近匹配才停下询问。
- **第二层（运行时）**：资源 URL 写进测试脚本，运行时由脚本自己下载到同目录。不在本地预下载——这样脚本换个环境也能跑。

### 4.3 踩坑经验的沉淀机制

`references/pitfalls.md` 是"活文档"，每次踩坑后追加实测记录（带日期）。分为四类：

- **页面探索与登录**：中文界面、滑块验证、单点登录互踢、菜单壳 404 陷阱
- **平台组件通用坑**：chint 下拉/虚拟表格/分页器/空态/表单校验的定位器写法
- **物化与运行环境**：CR-only 行尾、node_modules 解析、浏览器归一化
- **后端接口坑**：Nacos 发现与回退、双上传端点、save 语义、00001 排查法

这些坑不是"文档"，而是"Agent 写定位器前必读的检查清单"，显著降低重复踩坑率。

### 4.4 安全与隐私

- 给用户流式返回的内容中不出现 Uid 等隐私元数据（工具调用信息除外）。
- Hermes 凭据库 `/opt/data/auth.json` 永不触碰，Playwright 用各自的会话 `auth.json`。
- `functionUid` 占位符（如 `xxxx`）必须先询问用户确认，不猜测。

## 五、架构演进脉络

| 版本 | 架构 | 动因 |
|------|------|------|
| 4.x | MCP server + `.mcp/<pid>` 目录 + ppid 自发现 | 对齐 MCP 工作区模型 |
| 5.0+ | 纯 CLI + `/opt/data/e2e/<sid>` 真实目录 | 移除 MCP，消除进程模型漂移风险，Agent 与 CLI 同目录 |

演进的核心驱动力是**降低环境不确定性**：从"靠进程链推断工作区"到"Hermes 显式注入 sid"，从"每会话各自链接 node_modules"到"共享根 + 向上解析"。每一次简化都减少了一个故障面。

## 六、设计取舍小结

| 取舍点 | 选择 | 理由 |
|--------|------|------|
| 工作区隔离 | sid 真实目录 | 契约注入，不依赖进程模型 |
| 后端交互 | Python 脚本封装 | 固化踩坑逻辑，Agent 只传参 |
| 浏览器 | 强制 chromium | 容器统一，E2E 关心业务不关心浏览器 |
| 登录态 | 每会话独立 auth.json | 多会话并发不互踢 |
| 资源下载 | 运行时下载不预下载 | 脚本跨环境可移植 |
| 上传失败 | 不清理保留产物 | 待后端恢复续传 |
| 踩坑记录 | 活文档必读 | 避免重复踩坑 |

本技能的本质是：**把 AI Agent 的"理解与决策"能力，与固化的"机械操作"脚本结合，形成一个可自验证、可回传、可复用的 E2E 测试闭环**。Agent 负责对的不确定的部分（理解需求、探索页面、设计用例、修定位器），脚本负责对的确定的部分（拉配置、上传、清理），两者边界清晰，各司其职。
